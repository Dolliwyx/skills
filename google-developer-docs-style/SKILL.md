# Google developer documentation style

Produce clear, task-focused documentation for technical readers.

## 1. Resolve the applicable guidance

Honor explicit user requirements within the instruction hierarchy. For style choices the request leaves open, apply guidance in this order:

1. Project or product-specific requirements.
2. The [Google developer documentation style guide](https://developers.google.com/style).
3. Third-party references only when the preceding sources are silent.

Preserve established terminology and valid project exceptions. Prefer clarity and consistency over mechanical compliance.

## 2. Establish the reader and task

Identify the intended reader, what they need to accomplish or understand, prerequisites, and document type from the available context. Ask only when missing information would materially change the document.

For existing documentation, preserve its technical meaning. Flag uncertain facts instead of inventing details.

## 3. Draft, edit, or review

For review-only requests, inspect the documentation and report findings with suggested changes; rewrite or edit only when requested.

Use the core rules in [the review checklist](references/REVIEW-CHECKLIST.md). Organize content around the reader's goal, put required context before actions, and make the shortest complete path easy to scan.

When an exact usage question arises, consult the relevant live guide page linked in the checklist. Use the guide's [word list](https://developers.google.com/style/word-list) for disputed terms and spelling.

## 4. Review

Run one focused pass for each category in the checklist:

1. Structure and task flow.
2. Voice, grammar, and terminology.
3. Procedures, links, formatting, and code.
4. Accessibility and global readability.
5. Technical accuracy and internal consistency.

Resolve every applicable item. If project guidance intentionally differs from Google style, follow the project and mention the difference only when it affects review or maintenance.

## Output

For drafting or editing, return the finished documentation in the requested format. For a review-only request, return concise findings, suggested changes, and unresolved technical questions without modifying files. If the user also requests a rewrite, provide the revised text and a concise list of material changes.
