# Writing tickets

Turn notes, a conversation, or an existing ticket into a concise, self-contained title and body. Scale detail to the work; follow project templates and terminology.

## Ground the ticket

Use supplied evidence first; read relevant code, linked context, or tracker records when a missing fact could change the draft. Drafting does not authorize implementation or state-changing experiments. Preserve an existing ticket's facts and scope unless asked to change them.

Ask when a missing answer changes behavior, scope, or destination; otherwise, make useful unknowns explicit. Distinguish observations, reports, hypotheses, and proposals. Keep tentative suggestions tentative, and use only supported claims and metadata. Remove secrets and unnecessary personal data from evidence.

## Write the handoff

Write a specific title and lead the body with the problem or intended change and why it matters. Use plain words and only the headings needed to convey relevant evidence, scope, unknowns, and how completion is recognized. Link supporting detail rather than pasting investigation logs.

Make acceptance criteria observable outcomes, not speculative implementation tasks. For exploratory work, state the question to answer or finding to deliver. Keep independent work items separate; propose a split when needed.

Add a small, portable diagram only when it clarifies something prose cannot; distinguish proposed behavior from verified current behavior.

Check the draft against the source material. Return a copy-ready title and body, with clarification questions and publication discussion outside the ticket. Stop here for draft-only requests.

## Confirm and publish

Before any remote write, obtain approval of the displayed final draft and its exact destination, including the target issue for updates. A request to create a ticket alone is not draft approval. Reconfirm if the draft or destination materially changes; otherwise, existing approval suffices. Attachments need approval too.

Use authorized tracker tools and their supported operations. Apply only approved changes, preserving unrelated fields; approval of text does not authorize labels, assignments, scheduling, or workflow transitions.

Verify the saved title, body, and destination before returning the actual ticket URL or identifier. On failure, retain the draft and report the blocker and any known remote change. Inspect the destination before retrying an uncertain creation to avoid duplicates. Claim publication only after verification.
